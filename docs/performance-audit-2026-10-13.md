审查日期：2026-10-13。代码版本：`9c0d4dd`，应用 1.5.2。运行环境：macOS arm64、Node v24.20.0、项目安装的 Electron 43.4.1。

## 结论与优先级

发现 **1 项 P1、10 项 P2**，包括性能缺陷、会话刷新缺陷和容量/验证方面的隐患。最应先处理的是保存后的整库搜索重建、CSV 重复监听和索引日志清理失效；随后处理同步扫描、目录统计与长会话渲染。热搜索和单条 SQLite 更新本身较快，主要问题在其外围的全量加载、磁盘操作与 DOM 重建。

P1 表示应优先处理、会造成明显的秒级等待；P2 表示确定条件下影响流畅性、状态更新或长期容量。这里没有把所有同步 I/O、较大的源文件或单次 RSS 数值直接当作缺陷。

## 实测方法与对照数据

### 数据集与测量边界

- 原有基线：1,000 / 10,000 条很短的笔记，40 次热搜索、30 次更新。
- 扩展后端数据集：1,000 / 10,000 条约 1,032 个正文字符的中文/英文混合笔记，分布在 20 个分组及其子目录；每组数据还包含同数量的未同步 `.bin` 文件和一个 8 MiB 的未同步文件。因此万条后端同步场景实际遍历约 20,001 个文件，管理 10,000 篇笔记；该 8 MiB 文件只参与名称扫描，不用于证明大附件哈希耗时。
- 后端重复测量通常 12 次，保存后搜索 8 次，无变化同步 4 次；使用排序后的 nearest-rank P50/P95。4 次同步的 P95 就是该组最大值，统计稳定性有限。
- 目录计数独立使用 20 / 1,000 个叶目录，各带一层父目录，重复 6 次。只测 `treeForDocuments`，不含查询、网络或前端绘制。
- Electron 使用隐藏的 1280×850 窗口、关闭后台节流、隔离用户配置。数据库为 1,000 / 10,000 篇短笔记，另有一篇 1,000 个标题的约 5.3 万字符笔记、一份 80 列 CSV、100/1,000 条消息的两个会话。
- 界面耗时从发起操作到 DOM 条件满足并等待两帧，含约 15 ms 轮询误差；界面数据是单次场景测量，不能称为 P95，也不能代表打包应用冷启动。`startup` 仅从窗口载入页面到知识库入口出现，不包含 Electron/服务端进程启动。
- CSV 的滚动测量是同步派发滚动事件，记录处理时间和 MutationObserver 的 DOM 写入次数，不是完整的自然滚动帧率。
- 使用原始请求记录与 Long Tasks 观测辅助定位。没有调用真实 AI 服务，也没有测量外部网络、Windows 或低端设备。

## 发现及建议

### F01 — [P1] 保存后的搜索重新建立整库索引

位置：[search.js:138](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/search.js:138)、[search.js:149](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/search.js:149)、[search.js:120](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/search.js:120)。

任意笔记更新使 signature 改变。`load()` 即使已有内存索引，仍同步读取磁盘 records、创建 MiniSearch 并 `addAll`，随后才执行所谓增量更新；持久化也同步重写全部 records。多个文档变更时，每个 touched document 又反复过滤整份 records。

证据：千条保存后搜索 P95 253 ms，万条 2,803 ms；万条热搜索只有 19 ms。这段 CPU 和 JSON/磁盘工作在请求线程同步执行，其他搜索、保存和 Agent 工具请求也会排队。长正文和批量导入会继续扩大成本。

建议：利用已加载的 `mini`、`loadedSignature` 和按文档组织的 records 做真正增量变更；只有冷启动或日志断档才重建。持久化与索引构建放到可取消的后台任务/worker，并保持版本检查、原子安装及可回退重建。不要只把函数改成 `async`。

验收：单篇更新后不再触发整库 `addAll`；批量更新成本与变更记录相关；搜索一致性、索引断档恢复和数据库替换失效测试继续通过。

### F02 — [P2] 无变化同步仍重复读取和哈希全部文件

位置：[folder-sync.js:618](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/folder-sync.js:618)、[folder-sync.js:647](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/folder-sync.js:647)、[folder-sync.js:158](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/folder-sync.js:158)。

每轮先读所有 Markdown 收集图片，再在主循环重新读正文。判断 fingerprint 是否变化前已完整同步哈希文件，Markdown 最后还会再次计算 fingerprint。未变化的二进制也在比较前完整哈希。每 25 个文件让出事件循环没有限制一个批次的字节量或处理时长。

证据：一轮无变化万条同步仍有 20,000 次 Markdown `readFileSync`，读取约 48.5 MB，不包括 `readSync` 哈希读取；整轮 P95 1,469 ms，最大事件循环延迟 116 ms。当前实现默认还有 30 秒周期扫描及文件监听触发。单目录的未同步项查询也重新遍历整个根目录。

建议：维护变更路径队列和目录/图片依赖缓存；优先处理受影响路径，定期做低优先级完整校验。文件 stat 可作为调度提示，但不能替代写入前的完整 fingerprint 冲突检查。按时间/字节预算分批，将哈希与扫描移出服务请求线程；保留根边界、符号链接与原子写入保护。

验收：无变化扫描不重复解析全部笔记；大附件批次可中断；同步期间编辑与搜索仍可响应；同大小/mtime 的外部修改最终可发现。

### F03 — [P2] 目录统计为文档数乘目录数

位置：[routes.js:240](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/routes.js:240)、[workbench.js:5231](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:5231)。

`countFolder` 为每个目录重新遍历全部 documents，目录嵌套不会消除重复扫描。前端常规列表/搜索刷新默认先请求完整 tree，进一步把统计成本放进操作的串行路径。

证据：万条文档、40 个目录节点时约 8 ms；2,000 个节点时约 315 ms（P95 318 ms），尚未计入整库正文读取。目录节点和文档同时增多时接近二次增长。

建议：一次遍历建立各路径直接计数，随后按层级汇总子目录总数；以元数据版本缓存目录快照。搜索输入变化不应重取未变化目录统计。

验收：同一批文档增加目录时不再重复扫描整库；空目录、归档、应用包过滤与多知识库计数保持一致。

### F04 — [P2] CSV 编码/分隔符切换会累积监听器

位置：[filePreview.js:230](/Users/ranran/Documents/ChatGPT/liuxu/public/js/knowledge/filePreview.js:230)、[filePreview.js:249](/Users/ranran/Documents/ChatGPT/liuxu/public/js/knowledge/filePreview.js:249)。

每次 `draw()` 调用 `renderGrid()`，后者向同一个 viewport、table 和搜索控件新增监听器，却没有释放上一组。旧闭包仍持有旧解析 rows。一次滚动会运行所有旧 `renderRows`；搜索、单元格点击和复制监听也会累积。虚拟行限制了显示行数，却没有消除重复全表过滤和重复绘制。

证据：10,000×80 CSV，初始 8 次派发滚动对应 8 次表格重绘；切换编码三次后，一次滚动重绘 4 次，处理约 39.4 ms，初始通常约 9–10 ms。1,000 行同样复现 4 次重绘，约 50.8 ms；不要根据这两个单次数据推导行数与时间的严格关系。

建议：给 grid 返回 disposer，重绘前释放旧监听器；或绑定一次事件，只替换当前 rows 状态。匹配结果在 query/data 改变时计算，滚动只切片；通过一帧一次的调度合并滚动绘制。

验收：连续切换编码/分隔符 20 次后，每次滚动、搜索和复制都只执行一次；旧 rows 可释放。

### F05 — [P2] 索引变更日志清理检查发生在版本增加之后

位置：[documents.js:771](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/documents.js:771)、[documents.js:786](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/documents.js:786)。

清理仅在写操作 `touchIndexVersion()` 增加当前版本后触发；此时磁盘 indexVersion 至少落后一轮，`current > persisted` 会直接退出。搜索持久化完成后没有另一个清理入口。因此正常单进程保存/搜索流程不能按注释的意图清理已消费日志。

证据：新库创建一篇笔记后，600 次更新且每次都搜索；结束时当前和磁盘索引版本均为 601，变更表仍保留 601 条记录。每 200 次写入的清理尝试还会同步解析整份 records JSON，却没有删除日志。

建议：索引成功原子持久化后清理已确认消费的版本；或仅删除安全的 `<= persistedVersion` 前缀，明确处理所有索引消费者和回退策略。不要删除尚未消费的变更。

验收：持续保存/搜索后变更表收敛到受控窗口；持久化失败、索引落后、重启或缺失索引仍可正确重建。

### F06 — [P2] 长会话取回及渲染缺乏窗口边界

位置：[store.js:41](/Users/ranran/Documents/ChatGPT/liuxu/lib/agent/store.js:41)、[workbench.js:3371](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:3371)、[workbench.js:3341](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:3341)。

会话详情查询取回所有消息；切换时清空容器并同步生成全部可见消息、Markdown 和 traces。32 个详情缓存与 500 项 Markdown 缓存只有条数上限，没有字节预算。消息量与单条消息长度同时增长时，请求和 DOM 成本直接增长。

证据：千条消息会话打开约 383–409 ms；另一份约千字/条的千消息后端夹具返回 JSON 为 2.36 MB。热数据库读取仅约 5 ms，说明不能只优化 SQL。千消息界面新增约 26,550 个元素；Long Tasks 记录到切换阶段约 256 / 107 ms 任务。

建议：消息 API 增加向前游标，先取最新窗口，滚动时补历史；前端使用窗口化消息及 traces，避免切换时整段同步重建；详情/Markdown 缓存加入字节预算。历史存储继续保留，默认窗口不等于删除历史。

验收：长会话首次显示成本不再随全部历史线性增加；历史加载、回放去重、滚动锚点与后台运行返回均正确。

### F07 — [P2] 分页限制未限制底层正文读取

位置：[routes.js:396](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/routes.js:396)、[documents.js:751](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/documents.js:751)、[documents.js:1380](/Users/ranran/Documents/ChatGPT/liuxu/lib/knowledge/documents.js:1380)。

列表先 `allDocuments()` 读出、解析并多次 normalize 所有 JSON 正文，再过滤、排序和 slice。快速打开和 `searchDocuments` 也读整库；`hydrateFilePreview` 为修复标题读取整个 store，所以打开一个导入文件也受整库正文体积影响。`limit=20/60` 只减少返回量。

证据：万条约千字笔记，内存分页路径 P95 79 ms、快速打开 84 ms、文档搜索汇总 97 ms。真实界面的万条短笔记列表请求约 16–18 ms，说明正文长度很重要。前端连续加载更多也每次重新生成已加载的所有行，600 条时页面接近 1.8 万元素。

建议：为常用元数据增加适当列/表达式索引，过滤和稳定排序分页下推 SQL；列表仅投影必要摘要，单文件修复按 id 查询。前端追加只处理新增行，较大列表采用窗口化；未同步项和文件夹也需要边界。

验收：分页不加载非当前页正文；排序游标稳定，置顶、归档、标签/日期过滤与 annotation 可见性不回退。数据库结构调整需迁移兼容已有 JSON body。

### F08 — [P2] 长笔记输入后同步重建完整预览

位置：[workbench.js:486](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:486)、[workbench.js:514](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:514)。

300 ms debounce 减少次数，但每次执行仍解析、清洗全部 Markdown、设置完整 innerHTML、处理目录、重新绑定图片和链接。长正文或大量标题时，停顿一次就会执行一段主线程工作；保存路径在分栏模式下还可能再触发预览。

证据：1,000 个标题、约 5.3 万字符笔记，分栏预览操作约 134–154 ms；每次新增少量文本的阶段出现约 70 ms 长任务。自动保存成功，最终目标笔记也正确，未发现这个夹具中的输入丢失。

建议：将可移出的解析阶段放到 worker，使用版本 token 丢弃旧结果；目录提取与 DOM 更新按变更部分/可视区域执行，并给大笔记设置自适应预览频率。Worker 不能替代主线程安全清洗和正确安装，也不能削弱 DOMPurify。

验收：持续输入、停顿、Ctrl+S 和快速离开文档时正文/版本一致，旧预览不覆盖新正文，光标与滚动位置稳定。

### F09 — [P2] hash 导航的重复路由处理可能取消缓存会话的刷新

位置：[workbench.js:3436](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:3436)、[workbench.js:3468](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:3468)、[workbench.js:6752](/Users/ranran/Documents/ChatGPT/liuxu/public/js/workbench.js:6752)。

同时绑定 `popstate` 和 `hashchange`。一次 hash 路径导航可能调用两次 `applyRoute`；第一次立即应用缓存会话并开始刷新，第二次增加 routeSerial 后，在 `prevId===id` 快速返回。第一次请求因此被序号检查丢弃，新内容不会安装。此条件在已缓存会话发生其他客户端/后端更新时有实际影响。
