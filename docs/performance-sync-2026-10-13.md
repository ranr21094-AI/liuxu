# 自动同步优化实施与验收（2026-10-13）

三处方案已实现：按路径处理通知、后台内容校验、增量清单与事务恢复。HTTP 接口保持兼容；默认设置迁移为 5 分钟补查，深度校验间隔 15 分钟。最新千条、万条隔离测试达到本次性能目标，但万条重复测试出现过边界超标，不能将一次达标视为稳定上限。

## 实施范围

- `lib/knowledge/folder-sync.js`：650 ms 合并、连续事件最多 2 秒；路径队列去重、超过 1,000 项或不明确事件退回补查。文件和图片引用索引、目录子树同步、明确删除证据、持续复用监听器、监听错误退避。保存通知仍核对磁盘指纹，后续外部编辑不被时间窗口忽略。
- `lib/knowledge/sync-worker.js` / `sync-worker-client.js`：懒创建 Worker，读取、SHA-256 与 Markdown 解析移到后台；附件最多一个、1 MiB 分块。结果携带根代次、文档版本、读取前后 stat；旧结果重新排队。主线程每 25 项或约 8 ms 让出，深度校验期间插入待处理通知。保存前仍执行完整冲突检查。
- 快照与增量：保留 `.liuxu/manifest.json`，追加带序号的 `manifest-deltas.jsonl`；闲置 2 秒或累计 100 项后后台压缩为快照。启动回放、末尾半行处理、损坏保留与目录复核；无变化不重写快照。
- `lib/knowledge/documents.js`：最外层 SQLite 提交前持久化恢复所需清单，提交后清理操作记录；失败恢复旧文件、遇到新外部正文保留冲突。去掉同一次保存第二次重复写恢复日志，提交后完整映射从 SQLite 恢复。
- ZIP、恢复、退出：导出固定快照和增量副本；合并忽略其他工作区的清单与恢复备份；恢复前取消旧 Worker。正常退出等待落盘；服务端长连接最多等待 4 秒后关闭，单工作区落盘失败不阻止其余工作区尝试退出。
- `lib/knowledge/search.js` / `documents.js`：性能验证发现搜索仍两次读取整库候选元数据，改为 MiniSearch 命中后只查询候选 ID。保持过滤、排序及返回数量语义。
- Electron 解包配置加入 Worker 及全部本地依赖；测试了真实 ASAR 的解包文件和 Node Worker 读取。未构建或运行完整桌面安装包。

## 验证方法

所有运行数据、密钥、数据库和目录均使用临时隔离位置；未读写用户真实知识库。`scripts/perf-sync.mjs` 使用真实多层目录和文件，1,000 / 10,000 条约千字正文笔记，加 8 / 64 / 250 MiB 实际写入的附件。每场景 30 次样本，通过 HTTP 并发搜索、读取不同文档和版本检查保存，同时执行后台文件校验。另测完整手动校验。
基线关闭后台监听和扫描，但保留正常保存到磁盘的流程，因此比较的是后台同步增量。搜索索引在计量前预热，附件与笔记创建后处于操作系统暖缓存；“启动扫描”测的是服务初始化及目录核对，不是完整 Electron 冷启动。P95 为样本排序后 95% 分位；事件循环使用 2 ms 分辨率计量。

规模验收断言在两种规模下均通过：外部修改一篇笔记的根目录遍历次数 0；应用保存后重放通知的根目录遍历次数 0、正文重复更新 0；无变化周期扫描保留快照修改时间。实际系统通知的正确性由监听模拟回归覆盖，未将模拟视为桌面通知到达时间实测。

## 重复结果与剩余阻塞

- 万条优化前一组：8 MiB 场景事件循环 P95 20.69 ms，未达 20 ms；完整校验 2.35 ms。记录见 `10000-before-journal-optimization.json`。
- 去除重复日志落盘后的非诊断一组：8 MiB 为 22.81 ms，其余附件 18.42 / 2.62 ms，完整校验 2.78 ms。请求 P95 最大增量 4.23 ms。记录见 `10000-borderline.json`。
- 同版本诊断一组：事件循环 P95 15.07 / 15.61 / 2.55 ms，完整校验 2.30 ms，全部目标通过。记录见 `10000-diagnostic.json`；启用计时包装，不能当作完全同条件的非诊断重复样本。
- 诊断显示正常保存 `updateDocument` P95 约 10 ms；恢复日志和增量清单的两次前台 fsync 每次通常约 4 ms，64 MiB 场景个别 fsync 达 19.64 ms，保存最长 46.45 ms。保存与搜索共享主线程，请求并发时这些工作影响全部请求。已消除整库搜索查询和重复恢复日志写入，剩余需要落盘的保存流程仍受磁盘负载影响。
- 要进一步压低尾延迟，应把保存文件及持久化步骤改成异步协调，并保持 SQLite 提交与文件恢复协议；这属于下一步架构调整，不能直接删除 fsync 或削弱保存冲突检查。本次没有以一次成功结果掩盖边界失败。

## 正确性回归与故障注入

新增增量同步回归覆盖：单路径与自行写入、连续通知和队列溢出、目录移动删除与空目录、图片依赖、同步中继续编辑、相同大小及时间戳的外部修改、Worker 过期结果/退出/根切换、增量尾部半行/完整损坏、清单写入失败、SQLite 失败、未提交和已提交操作的重启恢复、快照安装中断与取消清理、ZIP 合并隔离、禁用根目录及退出失败。原有冲突草稿、正文版本、原文件历史与 ZIP 往返测试一并复测。
最终隔离全量回归：621 项中 620 通过、1 跳过、0 失败，耗时 34.69 秒；包含新增 18 项同步回归。最后的退出失败隔离与恢复专项回归 19 项通过。

## 限制与兼容性

- macOS arm64、Node v24.20.0、本地磁盘。未验证 Windows、网络目录、冷磁盘、完整 Electron GUI 长任务和实际输入延迟；未实测万条以上。
- 后台校验测量对象主要为无正文变化的大附件和完整笔记哈希；大批新增 Office/PDF 的文本提取、批量首次导入和所有文件同时变化的最坏情况未纳入目标计量。
- 5 分钟补查主要检查路径和快速文件状态；无通知且大小与时间戳相同的修改依赖 15 分钟深度校验或手动同步。
- HTTP 同步、状态和保存接口兼容；配置版本升为 2，旧清单直接读取。降级旧版本前必须正常退出并生成完整快照。异常退出后应由支持增量的版本先恢复。

复测命令：`npm run perf:sync`；万条严格验收：`PERF_DOCS=10000 PERF_STRICT=1 npm run perf:sync`；诊断：再加 `PERF_TRACE=1`。原始 JSON 位于同名报告目录。
