# 文件工作区性能优化与复测（2026-10-14）

本次实现将服务可用和后台索引拆开。已有 SQLite 文档索引及身份记录可先供界面使用，文件核对和索引在后台继续；首次发现按批次发布文档。轻量扫描先遍历目录并比较文件状态，只有文件变化、索引缺失或明确执行深度校验时才读取正文、计算完整哈希或更新索引。读取和保存仍核对磁盘指纹，不以状态缓存替代冲突保护。

扫描观察缓存位于新建的 SQLite 派生表 `knowledge_file_observations`，保存路径、指纹和文件状态；文档身份仍保存在 `.liuxu` 旁路记录。SQLite 缓存缺失或不匹配时重新核对。索引队列仅保存文档 ID、路径和基准信息，按文档版本丢弃过期任务。索引失败不回滚已落盘文件，并按退避计划重试。

## 复测结果

测试于 macOS arm64、Node 24.20.0 在临时目录和隔离 SQLite 完成，没有访问正式用户数据。搜索和磁盘缓存已预热；请求采样期间运行一次后台核对。旧值取自同日提交前的[原始基线报告](performance-file-workspace-2026-10-14.md)，新值取自本次版本的独立运行，不能替代多轮稳定性结论。

本次已有索引重启后，全部 1,000 条列表约 206 ms 可用，10,000 条约 2,583 ms 可用；后台核对及索引基线复用后分别为 237 ms、2,848 ms。首次建立工作区时，在 1,000 条约 73 ms、10,000 条约 157 ms 后可以列出首批 8 条，扫描继续分批增加。两种规模的无变化扫描均为正文读取 0 次、完整哈希 0 次、索引写入 0 次，并跳过全部已有文档。10,000 条首次建立身份、旁路记录和搜索索引仍需约 36.7 秒，但不再挡住首批文档显示和读取。

同一进程中再次创建第二个工作区时，旧对象尚未回收，RSS 会继续升高（本次万条样本为 700 MiB）。该值不代表全新进程的稳态占用。待处理索引队列不保留正文；本次内存仍会随知识库规模及搜索索引增大，后续应继续做重复扫描后的内存稳定性检查。

## 验收范围与未完成项

- 全量 `npm test`：662 项通过、2 项跳过；另有文件工作区与 SQLite 定向回归 37 项通过、1 项因当前平台不支持递归文件监听而跳过。
- 1,000 条请求类别各采样 30 次；10,000 条请求类别各采样 30 次。两次均为单轮独立运行，未达到五轮重复和每项 100 个请求样本的计划要求。
- 当前性能脚本数据仅为 Markdown 笔记。尚未覆盖 30／100／240 MiB 附件、PDF／Office 混合库、首次空索引以外的批量外部变化、反复三轮扫描内存增长或冷磁盘。
- 此环境运行 `npm run test:file-workspace:electron` 时 Electron 在进程启动阶段收到 `SIGABRT`，连 `--version` 也无法运行；本次 macOS 打包窗口验收未完成。Windows 文件监听、路径大小写与原子替换验收未完成。
- 后台任务影响通过扫描并发下的请求 P95 和事件循环延迟初步观察。万条样本的打开、保存、搜索 P95 分别为 9.28、37.68、13.36 ms；没有同一数据集下空闲与扫描状态各五轮的差值，因此不宣称已验证“交互 P95 增量不超过 50 ms”。
